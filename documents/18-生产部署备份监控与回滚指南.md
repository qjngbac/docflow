# 云笺 DocFlow 生产部署、备份、监控与回滚指南

## 1. 本次交付范围

项目已经具备以下生产运维基础：

- Flyway 数据库版本迁移，当前结构由 V1～V5 迁移共同建立：26 张业务表，另有 Flyway 历史表。
- MySQL 与上传文件的每日自动备份、SHA-256 校验、保留清理和显式恢复。
- Spring Boot Actuator、Micrometer Prometheus 指标、CRDT 健康检查。
- Prometheus 抓取、Blackbox 探测、核心告警规则和 Alertmanager 示例。
- Nginx HTTPS/WSS、HTTP 跳转、ACME 证书签发入口和安全响应头。
- 版本目录发布、发布前备份、健康检查失败自动切回上一应用版本。
- 数据库恢复与应用回滚分离，防止错误删除生产字段或覆盖数据。

这些文件不会自动修改本机数据库或申请证书。生产服务器仍需配置域名、证书、密码、告警接收人和 systemd 服务。

## 2. 数据库迁移

迁移目录：

```text
docflow/docflow-server/src/main/resources/db/migration
```

历史 `upgrade_*.sql` 只作为旧版本升级记录保留，不再由 Flyway 自动执行。它们存在重复字段、过程式判断和手工执行假设，不能直接改名后放进迁移目录。

### 2.1 全新空数据库

1. 先创建空数据库和应用账号，不要手工执行 `schema.sql`。
2. 配置 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD`。
3. 设置：

```text
FLYWAY_ENABLED=true
FLYWAY_BASELINE_ON_MIGRATE=false
```

4. 启动 Java 服务，Flyway 会依次执行 V1～V5，并创建 `flyway_schema_history`。
5. 检查日志和表结构后再开放流量。

### 2.2 已有业务数据、尚未由 Flyway 接管的数据库

已有数据库不能再次执行 V1。首次接管时：

1. 执行一次完整备份并通过 `verify-backup.sh`。
2. 对照 `V1__baseline.sql` 确认 23 张基线表、字段和索引已经完整，不能只比较表数量。当前 `schema.sql` 已含 V3/V4 新表，不应用它重新初始化旧库。额外的 `doc_client_state`、`doc_crdt_update`、`doc_edit_lock`、`doc_operation`、`doc_snapshot`、`file_asset` 是旧实现遗留表，首次接管时保留，不为迁移删除。
3. 第一次启动设置：

```text
FLYWAY_ENABLED=true
FLYWAY_BASELINE_ON_MIGRATE=true
```

4. Flyway 会把现有结构登记为版本 1，不再运行 V1，随后执行 V2～V5；核对历史记录和原数据后再开放使用。
5. 启动成功后永久改为：

```text
FLYWAY_ENABLED=true
FLYWAY_BASELINE_ON_MIGRATE=false
```

如果数据库只执行过部分旧升级脚本，不得直接 baseline。应先在隔离测试库补齐并核对结构，再处理生产库。

已有 `flyway_schema_history` 的数据库正常升级即可，保持 `FLYWAY_BASELINE_ON_MIGRATE=false`。存在失败记录或校验和不符时先查明原因，不自动 repair、删除历史表或将基线跳到 5。

### 2.3 当前新增迁移与版本兼容

| 版本 | 内容 |
| --- | --- |
| V2 | 通知类型加入 `ADMIN_MESSAGE` |
| V3 | `stored_file`、`stored_file_scope`，及头像/附件/反馈文件的历史关联 |
| V4 | `crdt_materialization` 队列与 `document.crdt_materialized_generation`；保留已有表/字段 |
| V5 | Java 迁移 `V5__legacy_file_references`，从正文、版本、模板补登记文件引用 |

V5 是 JAR 内的 Java migration，不能只执行两份 SQL 就认定升级完成。Node 对旧库仅可补建 outbox，不会补 Java 字段或文件权限表；只更新 Node 不能解决后端的缺表/缺字段问题。

迁移前暂停所有写入进程，在一致窗口备份数据库和 uploads；先用隔离副本演练，再成套更新 Java、Node 和前端。不要用本机数据库覆盖服务器数据。副本若启动应用，需隔离 Redis、文件目录和 Java API；当前 Node 广播不能靠 `REDIS_DATABASE` 隔离。

V5 不解码 Yjs。副本演练还需只读核对当前 checkpoint 与后续增量中的文件引用，避免未及时进入 HTML 的图片遗漏登记。发现问题先核实引用来源，不取消文件授权检查，也不重建原 Y.Doc。

生产还需核实上传绝对路径、Java/Node 的同库连接和管理密钥，以及 Secure Cookie。Nginx 的 `/files/` 必须转给 Java 授权控制器，不能用静态 alias 绕过检查。Java 不会自动加载旁边的 `.env`；当前默认 `file.upload-dir` 是 `./uploads`，示例中的 `FILE_UPLOAD_DIR` 占位符需由实际外部配置加载，不能仅添加环境变量就假设生效。

### 2.4 后续迁移规范

- 每次结构变化新增 `V2__...sql`、`V3__...sql`，已发布文件不可修改。
- 默认采用“扩展再收缩”：先加兼容字段或表，应用稳定后在后续版本移除旧结构。
- 禁止在普通发布中使用 `DROP TABLE`、`DROP COLUMN` 或破坏性类型转换。
- `spring.flyway.clean-disabled=true` 已禁止清库命令。
- 发布前执行备份，发布后检查 `flyway_schema_history` 的成功状态。

## 3. 自动备份与恢复

### 3.1 服务器文件

```text
deploy/scripts/backup.sh
deploy/scripts/verify-backup.sh
deploy/scripts/restore.sh
deploy/systemd/docflow-backup.service
deploy/systemd/docflow-backup.timer
deploy/backup.env.example
deploy/mysql-backup.cnf.example
```

将示例复制为服务器私有文件：

```bash
sudo install -d -m 0750 /etc/docflow /var/backups/docflow
sudo install -o docflow -g docflow -m 0600 deploy/mysql-backup.cnf.example /etc/docflow/mysql-backup.cnf
sudo install -o root -g docflow -m 0640 deploy/backup.env.example /etc/docflow/backup.env
sudo chmod 0750 /opt/docflow/deploy/scripts/*.sh
```

在 `/etc/docflow/mysql-backup.cnf` 中填写专用备份账号。该文件权限必须是 `0600`，密码不得写入 Git、命令行参数或日志。备份账号至少需要读取表、视图、触发器和事件；若启用存储过程备份，还需按 MySQL 版本授予查看例程定义的权限。

启用定时器：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now docflow-backup.timer
sudo systemctl start docflow-backup.service
sudo systemctl status docflow-backup.service
sudo systemctl list-timers docflow-backup.timer
```

备份默认每天 02:30 执行，随机延迟最多 15 分钟，保留 14 天。每份备份包含：

- `mysql.sql.gz`
- `uploads.tar.gz`；上传目录缺失时备份失败，不接受缺少文件的备份
- `metadata.env`
- `SHA256SUMS`

### 3.2 校验和恢复演练

```bash
/opt/docflow/deploy/scripts/verify-backup.sh /var/backups/docflow/20260804T023000Z
```

恢复必须在停止写流量后执行，推荐先恢复到新数据库并验收，不要直接覆盖唯一生产库：

```bash
export RESTORE_CONFIRM=RESTORE_DOCFLOW
export DB_NAME=docflow_restore_test
/opt/docflow/deploy/scripts/restore.sh /var/backups/docflow/20260804T023000Z
```

恢复后必须验证用户、文档、权限、CRDT checkpoint 与增量、历史版本、附件和分享链接。至少每季度做一次恢复演练。数据库 binlog 和对象存储版本控制属于进一步的时间点恢复能力，应在数据库或云平台单独启用。

恢复演练必须显式指定新测试库和独立 `UPLOAD_DIR`；`restore.sh` 默认使用业务库名和上传路径，不可直接照抄用于演练。`backup.sh` 不暂停写入，且包含按 `RETENTION_DAYS` 清理旧备份的操作，首次使用前先核实路径、保留规则和备份一致性。

## 4. 监控和告警

Java 管理端口默认是 `127.0.0.1:9091`，只暴露：

- `/actuator/health`
- `/actuator/health/liveness`
- `/actuator/health/readiness`
- `/actuator/info`
- `/actuator/prometheus`

Nginx 明确拒绝 `/actuator`，不要把 9091 开到公网。Prometheus 不在同一台机器时，应放在私网并使用防火墙白名单，不要直接改成公网监听。

安装并配置 Prometheus、Alertmanager、node_exporter、mysqld_exporter、redis_exporter 和 blackbox_exporter 后，将 `deploy/monitoring` 中的文件放入对应配置目录。必须替换：

- `https://docflow.example.com/`
- Alertmanager webhook 地址
- 各 exporter 的真实私网地址

加载前校验：

```bash
promtool check config /etc/prometheus/prometheus.yml
promtool check rules /etc/prometheus/docflow-alerts.yml
amtool check-config /etc/alertmanager/alertmanager.yml
```

当前告警覆盖 Java/CRDT/公网入口不可用、5xx 比例、p95 延迟、JVM 堆压力、磁盘不足、MySQL/Redis exporter 不可用、备份失败和备份超过 26 小时未成功。告警接收地址是示例，替换并实际触发一次测试告警后才算完成。

## 5. HTTPS 与证书

### 5.1 首次申请

1. 域名 A/AAAA 记录先指向服务器。
2. 只启用 `docflow-http-bootstrap.conf.example`，替换域名并运行 `nginx -t`。
3. 设置环境变量后申请证书：

```bash
export DOMAIN=docs.example.com
export CERTBOT_EMAIL=ops@example.com
sudo -E /opt/docflow/deploy/scripts/issue-certificate.sh
```

4. 将 `docflow.conf.example` 中域名和证书路径替换为真实值。
5. 执行 `nginx -t`，成功后再重载 Nginx。
6. 执行 `certbot renew --dry-run` 验证续期；将 `renew-certificate-hook.sh` 配置为续期 deploy hook。

生产只开放 80/443，8080、1234、1235、9091、3306 和 6379 只能由本机或受控私网访问。前端 CRDT 地址必须使用 `wss://`。

## 6. 发布和回滚

版本目录约定：

```text
/opt/docflow/releases/<release-id>/docflow-server.jar
/opt/docflow/releases/<release-id>/docflow-collab/
/opt/docflow/releases/<release-id>/docflow-web/
/opt/docflow/current -> /opt/docflow/releases/<release-id>
```

发布：

```bash
/opt/docflow/deploy/scripts/deploy-release.sh /opt/docflow/releases/2026.08.04-1
```

脚本会先备份，再切换 `current`，重启 Java 和 CRDT 服务，并检查 Java、CRDT 和可选公网地址。Nginx 直接读取 `current/docflow-web`，普通版本切换不需要重启。健康检查失败会自动切回上一应用版本。

脚本不自动安排维护停写、选择 Flyway 基线或验证旧协议回退。当前 Node `/health` 只证明进程存活；仍须验证登录、旧数据、文件权限、双端编辑与 HTML 回写，不能只看首页 200 或健康检查成功。

应用回滚：

```bash
export ROLLBACK_CONFIRM=ROLLBACK_DOCFLOW
/opt/docflow/deploy/scripts/rollback-release.sh
```

应用回滚不会自动恢复数据库，新增字段兼容不代表旧程序和新协议一定兼容。generation/outbox、旧 Node 回写和文件权限策略需在副本验证；不只回退某一个服务。需要恢复数据时先停止写入、保存故障现场，将备份恢复到新库及独立文件目录，验收后切换。恢复到发布前会影响之后的新修改，必须单独确认；禁止为回滚删除字段、队列或清理所有人的离线缓存。

## 7. 上线验收清单

- 新库已由 Flyway 建立，或已有当前库已完成一次 baseline。
- `flyway_schema_history` 无失败记录，`FLYWAY_BASELINE_ON_MIGRATE=false`。
- 手工备份成功，校验成功，测试库恢复成功。
- backup timer 已启用，Prometheus 能读取备份指标。
- Java readiness、CRDT health、公网站点和 WSS 均可用。
- Prometheus 规则通过校验，Alertmanager 已收到测试告警。
- HTTP 自动跳转 HTTPS，证书链正确，续期 dry-run 成功。
- 8080、1234、1235、9091、3306、6379 未暴露公网。
- 已执行登录、创建文档、两用户协作、附件、历史版本和导出冒烟测试。
- 已用预发布版本演练一次应用回滚，并记录恢复演练结果。
