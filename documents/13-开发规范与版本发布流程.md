# 云笺 DocFlow 开发规范与版本发布流程

## 1. 基本原则

- 以现有工程模式为主，不为小需求引入重复框架。
- Controller 只接入参数，Service 承载权限、事务和业务规则。
- 前端 API 集中在 `src/api`，用户提示统一转换为易懂中文。
- CRDT 使用成熟 Yjs 协议，不创建伪 CRDT 或 OT 兼容空实现。

## 2. Java 规范

- JDK 17，使用构造注入优先；避免新增字段注入形成循环依赖。
- DTO 使用 Bean Validation；不得直接信任前端 userId。
- 资源权限在 Service 层执行，管理员接口仍需后端拦截。
- 复杂事务明确 `@Transactional`，外部网络调用避免长时间占用数据库事务。
- 日志不输出密钥、Token、密码、验证码和完整正文。

## 3. 前端规范

- Vue 3 Composition API；公共状态放 Pinia，局部状态留组件。
- API 错误经过 `friendlyMessage`；危险操作使用项目对话框。
- 使用 Lucide 图标，图标按钮提供 `title`/可访问名称。
- 固定尺寸工具栏、按钮和页面轨道，避免动态内容引发布局跳动。
- 编辑器 schema 改动必须同步协作服务 schema 和导入导出转换。

## 4. CRDT 规范

- 不修改 Yjs payload，不依赖消息到达顺序。
- 更新写入必须有大小限制和持久化去重。
- checkpoint 必须事务化，先写后删。
- 管理端口不暴露浏览器；Java 与协作服务密钥保持一致。
- 新节点、mark 或 attribute 必须做双客户端和重启恢复测试。

## 5. 数据库规范

- 新表/字段更新 `schema.sql`，同时新增独立日期升级脚本。
- 升级脚本尽量可重复执行，先检查字段和索引是否存在。
- 不修改已在生产执行的历史脚本。
- 索引按真实查询创建，避免同列重复索引。
- 迁移前备份，迁移后校验。

## 6. Git 与提交

建议分支：`main`、`develop`、`feature/*`、`fix/*`、`release/*`。提交信息使用：

```text
feat: add feedback management
fix: restore navigation from admin page
test: cover owner CRDT access
docs: update deployment guide
```

一次提交聚焦一个主题，不提交 `node_modules`、`target`、真实 `.env`、日志和上传文件。

## 7. 测试要求

- 修改 Java：运行相关 JUnit，影响共享逻辑时运行 `mvn test`。
- 修改 CRDT/schema：运行 `npm test`，并做双用户协作测试。
- 修改前端：运行 `npm test` 和 `npm run build`，页面变更做桌面/移动截图检查。
- 修改数据库：在备份副本测试全新建库和已有库升级。

## 8. 代码评审检查

- 是否存在越权、敏感日志或硬编码密钥。
- 事务边界和失败回滚是否正确。
- 新接口是否统一响应并更新文档。
- CRDT 是否可能全量覆盖或删除未 checkpoint 增量。
- 文件路径、MIME、大小和 HTML 是否校验。
- 前端加载、空、错误、禁用和移动端状态是否完整。

## 9. 发布流程

1. 冻结发布范围，更新版本记录。
2. 运行 Java、CRDT、前端测试与构建。
3. 备份数据库和上传文件。
4. 在预发布环境执行迁移和冒烟。
5. 发布 Java、CRDT、前端。
6. 验证登录、文档、协作、保存、上传、导出和后台。
7. 观察错误率、日志和数据增长。
8. 完成验收或按预案回滚。

## 10. 文档同步

- 需求变化：更新 03。
- 架构/流程变化：更新 01、02、10。
- 表结构变化：更新 04。
- 接口变化：更新 05 和 Postman 手册。
- 配置/部署变化：更新 06、09、11。
- 发布：更新 14 和验收清单。
